# Ревью кода Flurry (v0.2.0 → v1.0.0)

Дата: 13.11.2026. Просмотрены все файлы репозитория: 11 модулей на Rust (~5,5 тыс. строк), HLSL-шейдер, build.rs, ресурсы, CI и скрипты в `tools/`.

## Итог в двух абзацах

Проект в хорошем состоянии: продуманная архитектура (два процесса, рендер в отдельном потоке, GPU-инстансинг, DirectComposition), аккуратная работа с ресурсами Windows и явное внимание к нагрузке. Для «одиночного» проекта такого объёма код читается легко, комментарии по делу.

Главные риски были не в графике, а в «долгой жизни» программы в фоне: потеря точности времени через несколько суток, фоновые сетевые запросы после выключения синхронизации, погода, которую временный сбой сети затирал, хук клавиатуры, который стоял всегда. Всё это исправлено в v1.0.0 (раздел 2). Оставшиеся замечания (раздел 4) не блокируют релиз.

Обозначения важности: 🔴 баг, заметный пользователю · 🟠 баг в редком сценарии / риск · 🟡 качество кода / производительность · ⚪ мелочь.

## 1. Архитектура

```
Flurry.exe            ← основной процесс (трей, хоткеи, IPC-окно)
 ├─ поток render             ← окна-оверлеи на каждый монитор, симуляция, D3D11 + DComp
 ├─ поток weather            ← Open-Meteo через WinHTTP, раз в 15 мин
 └─ Flurry.exe --settings  ← отдельный процесс, egui (glow)
        ↕ settings.json / weather.json + WM_APP-сообщения скрытому окну "Flurry.Ipc.v1"
```

Сильные стороны:

- **Окно настроек — отдельный процесс.** egui/OpenGL тянут десятки мегабайт; закрыли окно — память вернулась системе. Отличное решение для программы, живущей в трее.
- **Один источник правды для «эффективных» настроек** (`auto::effective`) используется и рендером, и превью в UI — превью показывает то же, что на экране.
- **Полный покой при выключении:** окна уничтожаются, D3D-устройство освобождается, поток спит в `MsgWaitForMultipleObjectsEx`.
- **Темп кадров по такту композитора** (`DCompositionWaitForCompositorClock`) с запасным путём на high-resolution waitable timer.
- **Туман и молнии в слое 1/8 разрешения**, растягиваемом композитором, — дешёвый и правильный приём.

Слабые места архитектуры:

- Связь процессов через файл + «перечитай» (`RELOAD`) — простая, но с гонкой записи (см. 4.4).
- `ui/mod.rs` — 1,5 тыс. строк в одном файле; страницы стоит разнести по модулям.
- Нет `rustfmt`: строки до ~300 символов, `cargo fmt --check` даёт 236 расхождений.

## 2. Что исправлено в v1.0.0

| # | Важность | Где | Проблема | Исправление |
|---|---|---|---|---|
| 1 | 🔴 | `render/mod.rs` `run` | Время анимаций `now as f32` теряет точность: через 1 сутки шаг ≈ 8 мс, через 10 суток ≈ 60 мс. Покачивание, мерцание светлячков, порывы ветра начинают идти «ступеньками». Программа с автозапуском легко живёт неделями. | `t = (now % 3600.0) as f32`. Раз в час — незаметный скачок фазы синусов (позиции частиц не прыгают). |
| 2 | 🔴 | `auto.rs`, `ui/mod.rs`, `app.rs` | Город сравнивался `eq_ignore_ascii_case` — для кириллицы это обычное сравнение с учётом регистра. «москва» ≠ «Москва» → погода молча игнорируется. Нашёл новый юнит-тест. | Функция `auto::same_city` (trim + `to_lowercase`) во всех трёх местах. |
| 3 | 🔴 | `app.rs` `spawn_weather` | Ошибка сети (Wi-Fi отвалился на минуту) перезаписывала `weather.json` состоянием с ошибкой → 15 минут эффект откатывался на сезонный, UI показывал «Не удалось получить погоду». | Если старые данные по тому же городу свежие (< 3 ч) — ошибка только логируется, данные остаются. |
| 4 | 🟠 | `app.rs` | После выключения «Погоды за окном» (или ручного выбора режима) поток погоды продолжал раз в 15 минут ходить в сеть с последним городом. Лишний трафик и неожиданно для пользователя с точки зрения приватности. | `App::sync_weather_thread()`: при выключенной синхронизации поток получает пустой город и перестаёт опрашивать. Вызывается из `reload`, `set_mode*`, трея, `WEATHER_REFRESH`. |

## 4. Что осталось (рекомендации на v1.1+)

1. 🟡 **Окно настроек перерисовывается 60 раз в секунду всё время, пока открыто** (3.11 `update`). Самое заметное место по нагрузке, которое осталось.
2. 🟠 **Нет повтора создания swapchain**, если оно не удалось для всех мониторов (3.8 `Mon::new`).
3. 🟡 **Геокодер берёт первый результат** и вызывается каждые 15 минут (3.5). Выбор из нескольких городов + кэш координат.
4. 🟠 **Гонка записи `settings.json`.** UI сохраняет с задержкой до 80 мс; если в этот момент пользователь нажал хоткей (основной процесс тоже пишет файл), одно из изменений потеряется. Редко и некритично. Полное решение — единственный владелец файла (основной процесс), а UI шлёт изменения через IPC (`WM_COPYDATA`).
5. 🟡 **Таблицы параметров режимов в трёх местах** (`sim.rs`, `widgets.rs::preview`, `render::auto_fps`).
6. 🟡 **Разбить `ui/mod.rs`** на `ui/pages/*.rs`; вынести части главного цикла рендера.
7. ⚪ **rustfmt:** добавить `rustfmt.toml` (`max_width = 140`), один раз `cargo fmt` и включить `cargo fmt --check` в CI.
8. ⚪ **Командная строка:** `--help`, ошибка для неизвестного `--mode`, ненулевой код возврата, если программа не запущена.
9. ⚪ **Битый `settings.json`** — сохранять копию перед перезаписью.
10. ⚪ **Подпись exe.** Без неё SmartScreen пугает пользователей. Для open source есть бесплатная подпись через [SignPath Foundation](https://signpath.org).
11. ⚪ **Название.** Решать вам, но слово в названии — грубый сленг. На GitHub это может отпугнуть часть аудитории и затруднить попадание в каталоги (winget, Scoop, обзоры). Если проект будет продвигаться, стоит заранее подумать о нейтральном названии (имя exe и путь в `%APPDATA%` тогда тоже поменяются — нужна миграция настроек).

## 5. Идеи новых функций

**Самое востребованное:**

- **Режим «только на рабочем столе»** — частицы за окнами, поверх обоев (окно-потомок `WorkerW`, как делают Wallpaper Engine и Lively). Многим нужен именно «живой фон», а не оверлей поверх работы.
- **Снег оседает на верхних краях окон** и тает, когда окно двигают — классический «вау»-эффект. Позиции окон есть через `EnumWindows`/`DwmGetWindowAttribute(DWMWA_EXTENDED_FRAME_BOUNDS)`.
- **Английский интерфейс** (простой `fn tr(key)` + 2 таблицы) — заметно расширит аудиторию на GitHub.

**Новые режимы:** звездопад (ночью), новогодняя гирлянда по верхнему краю экрана, мыльные пузыри от курсора, туман/дымка, град (уже есть коды WMO 96/99), осенние семена-«вертолётики» клёна, пыльца/пух тополя, морские брызги, тлеющие угольки.

**Удобство:**

- проверка обновлений через GitHub Releases API (раз в сутки, отключаемая);
- расписание («не показывать 9:00–18:00 по будням») и «не беспокоить»;
- свой режим на каждом мониторе;
- погода в подсказке трея и плавное изменение силы осадков без смены режима;
- праздничные режимы по дате (Новый год, 8 Марта — тюльпаны, Хэллоуин — летучие мыши);
- портативный режим: `settings.json` рядом с exe, если там есть файл `portable`;
- пакеты winget и Scoop.

**Для разработчика:**

- интеграционный «прогон» симуляции без окна (уже почти есть — `Field` не зависит от GPU): 10 000 кадров с разными настройками без паник и NaN;
- бенчмарк `Field::update/emit` (`cargo bench` или простой тест с замером);
- скриншоты README в CI через `HZ_UI_DEMO`.
